# CLAUDE.md — Escape from Saturn

Guidance for Claude Code when working in this project. These are accumulated
decisions; follow them unless the user overrides.

## Project

**Escape from Saturn (EfS)** is a MAD-65 game: a heavily expanded *Asteroids*
descendant with a story campaign, vector graphics, a large wrapping world and a
rotating/zooming camera. It lives at `D:\GitHub\EfS` and is **self-contained** —
`madsim.exe` and the system ROMs in `roms/` are bundled.

The **firmware** (CPU1 OS + GPU OS) lives in the *separate* MAD-65 repo
(`D:\GitHub\MAD-65`). After any firmware change: rebuild there (`make` in `roms/`)
and **recopy** `cpu_os.bin` + `gpu_os.bin` into `EfS/roms/`.

`D:\GitHub\CETAS` is the sister project — the first MAD-65 game, and the
structural template for this one (cart.cfg / Model B bootstrap / asset tooling /
Makefile shape). Read it before inventing a new pattern.

**Status: the game is real code and lives in `src/`,** built from the repo root
with `make` (`make run` for madsim, `make preview` for the headless check). It
began as a byte-for-byte promotion of `proto/03_radar`, so it already flies,
collides and draws a radar.

**`proto/` is FROZEN.** The three benches are records of what each question
cost, not living code, and no build reads them. Never edit a bench, never fork a
`proto/04` — a new question is answered in `src/` unless it genuinely cannot be,
and everything under `tools/` points at `src/` on purpose.

## Where the design lives

- [`docs/design_technical.md`](docs/design_technical.md) — the architecture, and
  section 11 lists the decisions that are **fixed**. Do not silently re-open them.
- [`docs/physics.md`](docs/physics.md) — the physics model and every tunable
  parameter. Parameters belong here, not scattered through the source.
- [`docs/open_questions.md`](docs/open_questions.md) — what is *not* decided, and
  how each item will be settled. When something gets settled, **move it** into
  design_technical section 11 and delete it here.
- [`docs/story.md`](docs/story.md) — narrative, written separately by the user.

## Working agreements

- **Test in madsim.** It simulates both CPUs cycle-accurately, plays the audio and
  paces to the real 60.317 Hz. The Verilator sim in the MAD-65 repo is for
  *hardware logic* only and is not the tool here.
- **Measure, do not guess.** Most numbers in the design are marked `(TBM)` — to be
  measured. The frame budget is ~237,000 cycles per CPU; madsim's F3 meter and F2
  dump report utilisation. Any claim about cost should come with a measurement.
- **Ship handling first.** Speed tiers, turn rate and camera lag (open_questions
  B1-B3) decide whether the game works at all. Prototype those before building
  content around them.
- **Physics is the long pole** and is expected to be re-tuned many times. Keep it
  parameterised and keep the headless soak test (physics.md section 8) working.
- **Do not use `mul16` in hot paths** — the engine's multiply is a quarter-square
  table. See design_technical 4.4.
- **The wrap is free.** Any code that tests for a world boundary is a bug: 16-bit
  overflow *is* the wrap, and a 16-bit subtract read as signed *is* the shortest
  distance across the seam.
- **TATE, clockwise**, per the MAD-65 house convention. Assets are pre-rotated;
  there is no runtime "vertical mode".
- **Build outputs are not tracked.** `cart.bin` and generated `assets/*.bin` are
  gitignored and regenerated by `make`. `madsim.exe` and `roms/*.bin` **are**
  tracked on purpose (self-contained repo). Never `git add -f` a build output.
- Assembler: `cl65 -t none --cpu 65C02`.
